# DMARC report viewer — integration design

Status: decided, not implemented. Written 2026-09-21.

Covers how dmarc-report-viewer should get its IMAP credentials, and how the
report mailboxes should be kept from growing without bound. The version bump
to 2.6.0, the `/health` status check and `DNS_SERVER=127.0.0.1:53` are already
in the tree; everything below is still to do.

## The problem

`setup/firstuser.sh` captures the first user's plaintext mail password at the
one moment it passes through the shell, encrypts it with `systemd-creds`, and
`dmarc_report_viewer.service` decrypts it at start. That couples a service
credential to a human's password, which gives us:

- It only exists on the non-interactive path. Interactively, `cli.py user add`
  prompts for the password itself and the shell never sees it, so there is no
  credential at all (the `EMAIL_PW` guard prints instructions instead).
- It is never updated when that user changes their password.
- It assumes the first user is the report receiver forever.
- `mailconfig.py` `kick()` rebuilds `dmarc-reports@` and `tls-reports@` as auto
  aliases pointing at `get_system_administrator()` on every run, so the
  receiver can move without `IMAP_USER` following it.
- A report viewer holds a credential that grants full mail access and
  control-panel login.

The code meant to keep this in sync is unfinished and, where written, wrong:

- `mailconfig.py:788` `store_dmarc_report_receiver_password` passes the literal
  string `<<<` as an argv element to `systemd-creds`. `<<<` is shell syntax; as
  written the function does not do what it looks like it does.
- `mailconfig.py:742` `get_dmarc_report_receiver` builds queries with
  unparameterised f-strings.
- Its three call sites in `set_mail_password` and `kick` are `# TODO` comments,
  so neither function is reachable today.

## Decision: a dedicated service mailbox

Create a real mailbox, `dmarc-viewer@PRIMARY_HOSTNAME`, with a password
generated by setup that no human ever sees. Point the two required report
aliases at it instead of at the administrator. The viewer logs in as that
account.

This removes the whole bug class rather than patching around it: no
interactive/non-interactive split, no coupling to a password change, no
first-user assumption, and rotation becomes `cli.py user password` plus
re-encrypt plus restart. Blast radius drops from "the admin's mail and the
control panel" to "a mailbox full of DMARC reports".

Rejected alternatives:

- **Dovecot master user.** No new mailbox and no delivery change, but a master
  credential opens every mailbox — a worse blast radius than the thing we are
  fixing.
- **Finish the TODOs.** Keeps a human's password in a service, is the most
  code, and still needs the interactive path solved separately.

### Sketch

- Setup step runs after `firstuser.sh` (needs the management daemon and a
  domain). Idempotent: create the account only when absent, generate and store
  the password only when the credential file is absent.
- Password: generated locally, written straight into
  `/etc/default/dmarc_report_password` via `systemd-creds`. Never echoed.
- The account is not an admin.
- `mailconfig.py` `kick()`: for `dmarc-reports@` and `tls-reports@`, target the
  service mailbox when it exists, falling back to the administrator when it
  does not, so existing installs keep working before the account is created.
- The global sieve keeps working unchanged. `fileinto :create "DMARC"` runs as
  the delivering user, which becomes the service mailbox, matching
  `IMAP_FOLDER_DMARC=DMARC` / `IMAP_FOLDER_TLS=TLSRPT`.
- The mailbox is created automatically if it does not exist.

### Costs, accepted

- The administrator stops seeing reports in their own mailbox and sees them
  only in the viewer UI.
- The account appears in the control panel user list.
- Existing installs need a migration step.

## Retention: 90 days

The viewer has no store of its own. From its README: *"All data is kept in
memory and retrieved each time fresh from the configured IMAP account."* There
is no `expunge`, no `delete` and no `\Deleted` anywhere in its source, so the
mailbox is the database, and every check interval (default 1800s) it re-fetches
and re-parses all of it. RAM, startup time and per-interval cost grow with
total mail ever received. The 2.4.0 duplicate filter dedupes the display, not
the mailbox.

Ninety days, because aggregate reports have a short half-life. What they are
used for — spotting an unauthorised sender, confirming an SPF or DKIM change
took effect, deciding when to move `p=none` to `quarantine` to `reject` — is
answered by the last few weeks. Thirty days would cover nearly all of it; 90
leaves headroom for "something started while I was away for six weeks". Beyond
that a report describes a sending landscape that no longer exists.

Two further reasons not to keep more: the long-horizon question ("is spoofing
of our domains trending up") is better served by scraping `/metrics`, which
2.5.0 extended with per-domain report metrics, at kilobytes instead of
hundreds of megabytes; and these reports are logs of third-party sending IPs,
so holding them indefinitely is a retention liability rather than an asset.

The cost, stated plainly: retention *is* the dashboard's time range.

### Mechanism

A line in `conf/cron/miab_dovecot` (which already runs `doveadm fts optimize
-A` daily), scoped to the service mailbox:

    doveadm expunge -u dmarc-viewer@<hostname> mailbox DMARC savedbefore <date>
    doveadm expunge -u dmarc-viewer@<hostname> mailbox TLSRPT savedbefore <date>

with the date computed absolutely (`date -d '-90 days' +%Y-%m-%d`). The doveadm
search docs describe `savedbefore` as taking a "date specification" and give
relative-interval examples only for `since`, so an absolute date avoids relying
on unverified behaviour.

Not `autoexpunge`, even though it is the more elegant mechanism and is still a
valid mailbox setting in 2.4.2. Dovecot 2.4 has no per-user config filter —
`user <address> { ... }` is rejected with `Unknown section name: user` — so a
`mailbox DMARC { autoexpunge = ... }` block would silently expunge a `DMARC`
folder in *any* user's mailbox, including one a user created by hand. This is
why retention is dependent on the service mailbox and not separable from it.

Deletion is permanent either way; neither route goes via Trash.

## Verified while deciding this

- `/health` returns 200 with no credentials and is registered after the auth
  middleware in `src/http.rs:66`; `/` returns 401 when `HTTP_SERVER_PASSWORD`
  is set. An empty `HTTP_SERVER_PASSWORD` still satisfies the required-argument
  check, so basic auth stays off behind nginx.
- 2.6.0 release assets keep the `linux-x86_64/dmarc-report-viewer` layout, and
  no config option was renamed or removed between 2.2.1 and 2.6.0.
- 2.4.1 fixed absolute links behind reverse proxies, which probably makes the
  `/dmarc-reports` rewrite in `conf/nginx-primaryonly.conf` obsolete — there is
  a test item for this in TESTING-26.04.md.
- `management/editconf.py` opens its target without creating it, so any
  `editconf` call must follow the `cp` that puts the file in place.
